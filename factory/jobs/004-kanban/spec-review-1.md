# Spec review
## Verdict
NEEDS WORK (small, fixable: one missing icon that will break rendering, one attribute-order trap in `wire:sort`, and some untestable or unspecified bits).

## Problems
1. **Requirement 14 / C: `flux:icon.grip-vertical` does not exist.** Free Flux ships only Heroicons (no `grip*` file in `vendor/livewire/flux/stubs/resources/views/flux/icon`), and the project has published only `book-open-text`, `chevrons-up-down`, `folder-git-2`, `layout-grid` in `resources/views/flux/icon`. Rendering it throws a view error and breaks every milestone page. Fix: add a step "run `php artisan flux:icon grip-vertical`" (this publishes the Lucide icon into `resources/views/flux/icon`, as was done for the others), or use an existing Heroicon such as `bars-3`. `ellipsis-horizontal` does exist.
2. **Requirement 13: attribute order matters.** In `supportWireSort.js` the `interceptInit` loop walks the element's attributes in order and does `return` when it meets `wire:sort:group` (only `wire:sort:group-id` is skipped with `continue`). If `wire:sort:group` appears before `wire:sort`, the `wire:sort` binding is never created and drops silently do nothing. The spec lists `wire:sort` first, which is correct, but does not say it must stay first. Add that constraint, and a Blade comment in the view. The HTML test in criterion 3 (substring count) can't catch a wrong order. Either assert the attribute order, or accept that the manual check covers it.
3. **Requirement 13 / handler semantics (verified, with one caveat).** `onSort` only calls the handler on the destination list, so a cross-column drop calls `moveTask` once. The position is `findIndex` among that list's `wire:sort:item` children, and the args are `(item, position, groupId)`, which matches `moveTask(int, int, string)`. `$item` is the evaluated item key, so `wire:sort:item="{{ $task->id }}"` arrives as a string or number; the `int` type hint coerces it. Fine. Caveat: the empty-column text must be outside the list, as B7/C13 say, otherwise it would shift nothing but would confuse the minimum-height drop target. Keep the list `min-h-*` itself, not the wrapper, or drops onto the padding won't register.
4. **Requirement 10, whole-milestone renumbering, uses `findTask()` then re-queries.** Say explicitly that the board order is built from one fresh `$this->milestone->tasks()->get()` inside the transaction (not from the cached `columns()` computed), or a second `moveTask` call in the same request sees stale data. Also `moveTask` should call `unset($this->columns)` (or rely on Livewire re-evaluating computed per request) so the progress shown after the move is fresh. Criterion 2 "page shows updated progress" covers this, but name the mechanism.
5. **Requirement 9 / 10: the menu "Move to" strings.** `__('Move to :status', ['status' => __($other->label())])` should be spelled out. The criteria assert "Move to In progress", which only works with the label change in A1. Note that `InProgress` is not translated anywhere else and no test or view currently references `'In Progress'` (grep confirms only the enum), so A1 is safe.
6. **Requirement 9: Edit/Delete moving into a dropdown changes existing tests' selectors?** Existing tests call Livewire actions directly, so they pass. But `editTask` still has no `authorize('update', ...)`, while the Context section says "authorize `update` in every write action". `editTask` is not a write, so this is acceptable; just state that so a reviewer doesn't add it.
7. **Requirement 3/4: Larastan and `withCount` properties.** `done_tasks_count` / `tasks_count` are undeclared on `Subject` and `Milestone` (the convention is `@property` docblocks). Blade isn't analysed so `composer types:check` passes, but if the count is read in PHP (the subject-total sum in Subjects\Show, requirement 4) Larastan level 7 may flag it. Fix: do the sum in the view via `$this->milestones->sum('tasks_count')`, or add `@property-read int|null $tasks_count` docblocks.
8. **Requirement 4: "no extra query" for the subject total** is untestable as written. Add an assertion, e.g. `DB::enableQueryLog()` around render, or drop the claim. Same for A3 "one query, not one per subject": give a testable form (query count with 3 subjects equals the count with 1).
9. **Requirement 2: `trans_choice` pluralisation key.** `'…task done|…tasks done'` with count `$total` makes "1 of 1 task done" and "0 of 2 tasks done"; fine. But `done` over `total` of 0 never reaches the string. State that `done <= total` is assumed and that the bar `:value`/`:max` are ints. Flux `progress` exists and sets `aria-valuenow`/`aria-valuemax`; confirm the component also sets `role="progressbar"` and an accessible name, or add `aria-label`.
10. **Requirement 6: `columns()` return type.** `array<string, Collection<int, Task>>` is fine for Larastan, but the view uses `$this->columns[$other->value]->count()` inside `wire:click` strings, which is evaluated at render time. This is OK. Make sure the "Move to … position" arg isn't computed from a column that excludes the moved task: since the task is in a different column, the count is right.
11. **Criteria 2: 422 test.** `abort(422)` inside a Livewire action is a `HttpException`, which `RequestBroker` rethrows through the exception handler, so `->assertStatus(422)` works the same way the existing `assertNotFound()` does. Verified. No change needed.
12. **Requirement 10: the enum claim.** Correct: `ImplicitlyBoundMethod::getImplicitBinding` uses `tryFrom`. Since the action takes `string`, the claim is moot; consider deleting that Context bullet as noise.
13. **Context claim on `withCount`** is correct (`$query->orders = null` at the cited area; the line number is close to 910). OK for both `Subject::tasks()` (HasManyThrough) and `Milestone::tasks()`.
14. **Concurrency / drag during edit.** If a task is being edited inline (`editingTaskId`) and another card is dragged, the edit form lives inside a draggable card. The handle limits drag starts, but a drop re-render must keep `editingTaskId`. Add a test: edit task A, `moveTask` task B, `editingTaskId` unchanged.
15. **Criterion 4 (manual)** requires "Docker running" and Herd at pathly.test, but this job runs in a worktree. Per CLAUDE.md worktrees use `php artisan serve --port=<port>` and a separate DB. Fix the URL/instructions.
16. **Scope.** Sentence-case label change and `x-progress-summary` are fine. Running Pint/Larastan per step ("`composer test` passes" after each of A, B, C) is good. Step C leaves B's menu fallback in place, good. No policy, migration or new route is needed; say so explicitly so the builder doesn't add one.
17. **Tests missing from the list:** a subject index test that another user's subjects are not shown (only "tasks not counted" is covered); `moveTask` with `position` on a task whose status equals the target and position unchanged (no writes, no error); a milestone with zero tasks renders three empty columns with "No tasks"; the moved-task `updated_at` behaviour (decide if renumbering should touch it).

## Questions for the human
1. Should in-progress tasks count toward progress at all (spec says no)? Fine for now, but it's a product choice.
2. A task moved with the menu goes to the bottom of the target column, and one moved to Done gets no timestamp. Do you want a `completed_at` later (this would affect the renumbering code)?
3. Is it acceptable that the menu "Move to" is always the end of the column rather than the top?
4. Is renumbering the whole milestone on every move acceptable given Phase 5 broadcasts a single-task change (every move may now touch many rows and so emit many events)?
5. Should the icon come from Lucide (publish via `flux:icon`) or stay within Heroicons?
